# Gemini UX 原型设计沟通手册

> 本文档用于与 Gemini 沟通 IPTV-Check 项目的 UX 重构，按步骤组织 Prompt，逐层推进设计。

---

## 第一步：项目背景（开场必发）

```
我需要你帮我设计一个 IPTV 直播源检测管理平台的原型图。

## 项目背景
这是一个帮助用户检测、管理和观看电视直播源的工具：
- 核心流程：选择直播源 → 检测有效性 → 查看结果 → 播放观看
- 用户痛点：直播源质量参差不齐，手动检测费时费力
- 目标用户：有 IPTV 观看需求的普通用户，技术能力参差不齐

## 现有页面
1. 源配置页（Source）- 入口页，选择在线源 / 上传本地文件 / 配置参数
2. 检测中页（Checking）- 实时进度展示，环形图 + 日志
3. 结果页（Result）- 结果列表 + 统计报告 + 趋势分析
4. 播放页（Live）- 频道列表 + 播放器
5. 工具箱页（Toolbox）- 格式转换、定时任务等辅助工具
6. 收藏页（Favorites）- 收藏频道管理

## 当前技术栈
- 前端：Vue 3 + Tailwind CSS + shadcn-vue
- 设计风格：现代简约，注重数据展示效率
- 图标库：Lucide Icons
- 参考风格：Google Material Design

## 当前 UX 痛点（按优先级排列）
### 高优先级
1. 用户选多个本地文件时，看不到上传进度，以为卡死
2. 18 个在线源需要逐个点击选择，缺少批量操作
3. 参数配置（超时、线程数）对新手不友好，缺少推荐预设
4. 点击"停止检测"无确认，误操作会丢失所有进度
5. 搜索结果无 loading 提示，用户以为没响应
6. 运营商检测失败后等待 10 秒才重试，体验差

### 中优先级
7. 实时日志一直展开，视觉干扰
8. 分组视图缺少"展开 / 折叠全部"按钮
9. 播放器切换频道无过渡动画，感觉生硬
10. 工具箱功能分散，新用户不清楚先用哪个
11. 源选择缺少"按评级全选"（如全选 S 级源）

### 低优先级
12. 移动端侧边栏占用空间
13. 历史记录无法快速对比两次结果差异
```

## 第二步：逐页沟通（按优先级依次发送）

### 2.1 源配置页（Source）—— 最高优先级

```
## 页面：源配置页（Source）
这是用户首次使用的入口，最关键。

### 当前问题：
1. 用户选多个本地文件时，看不到上传进度，以为卡死
2. 18 个在线源需要逐个点击选择，缺少批量操作
3. 参数配置（超时、线程数）对新手不友好
4. 运营商智能推荐不够突出

### 页面功能：
- 展示 18 个在线源（按运营商分类，有质量评级 S/A/B/C）
- 自动检测用户宽带运营商，推荐兼容源（标"推荐"标签）
- 支持上传本地 M3U 文件（可能多个，需拖拽 + 点击）
- 支持手动输入自定义源 URL
- 配置检测参数：超时时间、并发线程数、是否测速
- 一键开始检测

### 数据示例：
在线源列表（节选）：
| 源名称 | 运营商 | 协议 | 评级 | 分类 |
|--------|--------|------|------|------|
| 国内直播源 | 电信,联通 | IPv4 | S | 国内电视 |
| 移动专用源 | 移动 | IPv4 | A | 国内电视 |
| 国际频道源 | 全部 | IPv6 | B | 国际电视 |
| 央央广播源 | 全部 | IPv4 | A | 广播电台 |

### 我希望优化的点：
1. 增加批量选择入口（按评级、按运营商全选）
2. 文件上传增加进度反馈
3. 参数配置增加"推荐配置"预设（快速 / 标准 / 深度）
4. 运营商智能推荐更突出，减少用户选择成本

请给出这个页面的原型设计建议和布局方案，要求：
- 给出 2-3 种布局备选方案并对比优劣
- 标注关键交互区域
- 说明设计理由
```

### 2.2 检测中页（Checking）

```
## 页面：检测中页（Checking）
这是核心业务流程的等待页面。

### 当前问题：
1. 点击"停止检测"无确认，误操作会丢失所有进度
2. 实时日志一直展开，视觉干扰
3. 剩余时间预估不够准确

### 页面元素：
- 环形进度图（显示百分比）
- 四个阶段：解析 → 下载 → 检测 → 汇总
- 实时统计：有效 / 无效数量、成功率、耗时
- 实时日志滚动（可折叠）
- 停止按钮

### 实时数据示例（通过 SSE 推送）：
- 总频道数：256
- 已检测：128（50%）
- 有效：96，无效：32
- 成功率：75%
- 已耗时：2 分 15 秒
- 当前阶段：checking（第三阶段）

### 我希望优化的点：
1. 进度图增加阶段动画过渡
2. 日志默认折叠，点击展开
3. 停止按钮增加二次确认
4. 增加预计剩余时间的置信度提示（"预计 5-8 分钟"）
5. 考虑"最小化到后台"功能，让用户可以先去做别的事

请给出原型设计建议，同样给出 2-3 种备选方案。
```

### 2.3 结果页（Result）

```
## 页面：结果页（Result）
这是数据展示的核心页面。

### 当前问题：
1. 搜索结果无 loading 提示
2. 分组视图缺少"展开 / 折叠全部"按钮
3. 历史结果无法快速对比差异

### 页面功能：
- 视图切换：分组视图 / 平铺视图
- 搜索过滤（按频道名、分组），400ms 防抖
- 排序（按名称、延迟、速度）
- 三个子 Tab：结果列表 / 统计报告 / 趋势分析
- 统计报告（饼图：有效/无效占比，柱状图：分组统计）
- 趋势分析（折线图：多次检测的成功率变化）
- 导出（M3U / TXT / CSV / Excel）
- 智能优选（去重、保留最优源）
- 收藏操作（单个 + 批量）
- 加载历史检测结果

### 数据示例：
分组视图：
- 央视频道（12 个频道，10 有效 / 2 无效）
  - CCTV-1 ✅ 延迟 45ms 速度 5.2MB/s
  - CCTV-2 ✅ 延迟 62ms 速度 4.8MB/s
  - CCTV-新闻 ❌ 超时
- 卫视频道（8 个频道，6 有效 / 2 无效）
  ...

### 我希望优化的点：
1. 搜索框增加实时匹配数量提示（"匹配 23 / 256"）
2. 分组视图增加展开 / 折叠全部按钮
3. 增加批量操作工具栏（批量收藏、批量导出选中项）
4. 统计报告默认展示，让用户先看全局再钻细节
5. 考虑历史结果对比视图

请给出原型设计建议，重点关注信息层级和操作效率。
```

### 2.4 播放页（Live）

```
## 页面：播放页（Live）
这是用户的最终目标页面——看电视。

### 当前问题：
1. 播放器切换频道无过渡动画，感觉生硬
2. 频道加载时无 loading 状态
3. EPG 节目单信息占用空间

### 页面功能：
- 左侧：频道列表（按分组折叠，显示台标 + 频道名）
- 右侧：HLS 播放器（iframe 嵌入）
- 顶部：当前频道信息 + EPG 节目单（当前 / 下一个节目）
- 搜索频道
- 收藏频道快速访问

### 我希望优化的点：
1. 播放器增加频道切换加载动画
2. EPG 信息改为可展开面板，不占用播放区域
3. 频道切换增加过渡效果
4. 考虑沉浸模式（全屏播放，频道列表浮层切换）

请给出原型设计建议。
```

### 2.5 工具箱页（Toolbox）

```
## 页面：工具箱页（Toolbox）
辅助功能集合页。

### 当前问题：

### 我希望优化的点：
1. 增加功能引导（标注常用 / 进阶）
2. 功能卡片增加简短描述
3. 考虑按使用频率排序或分组

请给出原型设计建议。
```

## 第三步：交互细节确认

```
基于以上各页面的原型方案，我需要确认以下交互细节：

## 1. 整体布局风格
- 当前：桌面端左侧固定侧边栏 + 移动端底部 Tab
- 备选 A：保持侧边栏（信息密度高）
- 备选 B：改为顶部导航 + Tab（更现代感）
- 备选 C：侧边栏可折叠为图标模式（兼顾两者）
- 你的建议和理由？

## 2. 移动端适配
- 底部导航 vs 浮动菜单按钮（FAB）？
- 哪些功能在移动端可以简化或隐藏？
- 播放页在移动端的布局（竖屏看列表，横屏全屏播放）？

## 3. 关键交互决策
- 检测进度页是否需要"最小化到后台"功能？实现方式？
- 结果列表的批量操作入口放哪里最合理？（顶部工具栏 vs 右键菜单 vs 长按触发？）
- 源配置页：运营商推荐区域 vs 全部源列表，哪个更突出？

## 4. 信息层级
- 结果页默认展示：统计报告 vs 结果列表？
- 源配置页默认：在线源（推荐）vs 本地文件 vs 自定义源？
- 检测中页：进度图 vs 实时日志，哪个更突出？

## 5. 视觉风格
- 进度展示：环形图 vs 线性进度条 vs 阶段步骤条？
- 数据展示：卡片式 vs 紧凑表格 vs 混合模式？
- 空状态：插画 vs 图标 + 文字 vs 骨架屏？
- 错误状态：内联提示 vs Toast vs 弹窗？

## 6. 动效与过渡
- 页面切换：淡入淡出 vs 滑动 vs 无动效？
- 列表操作：展开折叠动画时长？
- 加载状态：骨架屏 vs Spinner vs 进度条？

请逐一回答并给出设计理由。
```

## 附录：补充 Prompt 模板

### A. 追问细节

```
关于 [页面名] 的原型方案，我还有几个问题：

1. [具体交互点] 在你的方案中是怎么处理的？
2. 如果 [极端场景]，用户会看到什么？
3. 这个方案对 [无障碍 / 性能 / 移动端] 有什么影响？
```

### B. 方案对比

```
我对比了方案 A 和方案 B，各有优劣：

方案 A 的优点：xxx
方案 A 的缺点：xxx
方案 B 的优点：xxx
方案 B 的缺点：xxx

综合考虑 [使用频率 / 实现成本 / 用户习惯]，你推荐哪个？为什么？
```

### C. 迭代修改

```
基于上一轮的原型方案，我需要调整以下内容：

1. [页面名]：[具体调整点] → [期望效果]
2. [页面名]：[具体调整点] → [期望效果]

请重新输出修改后的原型图。
```

## 💡 沟通技巧备忘

| 原则 | 说明 |
|------|------|
| **分步推进** | 不要一次性抛出所有需求，先定整体风格，再逐页细化 |
| **提供约束** | 明确技术栈和设计风格，避免推荐不适合的方案 |
| **要设计理由** | 每次询问都让 Gemini 解释"为什么这样设计"，便于判断 |
| **要对比方案** | 关键页面要求 2-3 种备选方案对比，不要只给一个 |
| **给数据示例** | 提供真实数据样例，让原型更贴近实际场景 |
| **考虑极端** | 空状态、错误状态、加载状态都要覆盖 |
| **追问细节** | 拿到初版后追问交互细节，不要一次就满意 |
